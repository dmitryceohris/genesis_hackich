# Контракт оценщика: findings, truth, сопоставление, награда

Статус: **предложение к заморозке**. Всё ниже выведено напрямую из задания
(разделы 03 и 05), а не придумано. Пока контракт не заморожен, зоны
«генератор/среда» и «оценщик/политики» не могут идти параллельно.

Правило: этот файл — источник истины для оценщика. Если генератор пишет
`truth.json` иначе, меняется генератор или этот файл, но не обе стороны молча.

---

## 1. Что приходит в `submit`

```
{
  "episode_id": "<string>",
  "findings": [
    {
      "type": "duplicate_invoice | payment_allocation | fx_conversion | period_cutoff",
      "affected_ids": ["<public_id>", ...],
      "claimed_amount_minor": <int>,
      "currency": "<ISO-4217>",
      "evidence_ids": ["<public_id>", ...],
      "explanation": "<string>"
    }
  ]
}
```

Жёсткие лимиты из задания (раздел 05):

| Ограничение | Значение |
|---|---|
| findings | не более 30 |
| evidence_ids на вывод | не более 10 |
| explanation | не более 1 000 символов |

## 2. Что лежит в закрытом `truth.json`

```
{
  "episode_id": "<string>",
  "issues": [
    {
      "issue_id": "<string>",
      "type": "<один из четырёх>",
      "affected_ids": ["<public_id>", ...],
      "expected_amount_minor": <int>,
      "currency": "<ISO-4217>",
      "acceptable_evidence_sets": [
        ["<public_id>", "<public_id>"],
        ["<public_id>", "<public_id>", "<public_id>"]
      ]
    }
  ]
}
```

Ключевой момент, который легко реализовать неправильно:
`acceptable_evidence_sets` — это **список наборов**. Каждый внутренний набор
достаточен сам по себе и целиком. Разные наборы — альтернативные способы
доказать одну и ту же ошибку.

## 3. Структурная валидация (отдельный путь, до метрик)

Задание: «Неверная структура завершает эпизод с наградой -1 и ошибкой в журнале
оценщика». Это **не** F1=0, а отдельная ветка кода.

Невалидно (итог −1, метрики не считаются):

- `episode_id` отсутствует или не равен текущему эпизоду;
- `findings` не массив;
- неизвестный `type`;
- `affected_ids` пуст или не массив строк;
- `claimed_amount_minor` не целое — в Python `bool` является подклассом `int`,
  поэтому проверять `type(x) is int`, иначе `true` пройдёт как 1;
- `currency` неверного формата;
- превышен любой лимит из раздела 1 (31 вывод, 11 доказательств, 1 001 символ).

Валидно структурно, но ничего не подтверждает:

- `evidence_ids: []` — допустимо, но ни один полный набор не покрыт, значит
  совпадения нет;
- выдуманный ID в `affected_ids` — допустимо, фактически FP.

Лимиты проверяются **до** удаления дублей внутри списка.

## 4. Нормализация (задание требует её опубликовать)

- ID — точные непрозрачные строки, **регистрозависимо**, без обрезки пробелов.
- `affected_ids` сравниваются как **множество** (порядок не значим).
- `evidence_ids` — множество.
- `currency` должна совпасть с эталонной; разные валюты не сравниваются без
  конвертации (задание, раздел 03).
- Допуск по сумме: **0 minor**, объявлен явно. Сумма неотрицательна (абсолютная
  величина расхождения), смысл задаётся полем `type`.
- `explanation` на совпадение **не влияет** — проверяется только структура и
  длина. Задание: «Награда зависит от полей и доказательств, не от убедительного
  текста».

## 5. Условие ребра «вывод ↔ эталонная ошибка»

Ребро существует, когда выполнены **все** условия:

1. `type` совпадает;
2. множество `affected_ids` совпадает с каноническим;
3. `currency` совпадает;
4. разница сумм по модулю не больше допуска (0 minor);
5. существует набор `S` из `acceptable_evidence_sets`, такой что `S` целиком
   содержится в `set(evidence_ids)`.

Пункт 5 — проверка подмножества, а не равенства и не пересечения. Лишние ID не
мешают совпадению, но и не заменяют недостающие.

## 6. Сопоставление: максимальное паросочетание, не жадный проход

Задание: «С эталоном взаимно однозначное». Жадный цикл `for finding: for issue:`
даёт неверный TP, когда один вывод подходит к двум ошибкам, а вторая ошибка
покрывается только им. Нужен двудольный граф и **максимальное паросочетание**
(алгоритма Куна достаточно: не более 30 × 12 рёбер).

При нескольких паросочетаниях одинакового размера выбор обязан быть
**детерминированным**, иначе ломается критерий «Воспроизводимость» (15 баллов) и
парные проверки жюри. Фиксируем правило: лексикографически первое по
отсортированному списку пар `(индекс вывода, issue_id)`.

Обязательный публичный тест: случай, в котором жадный выбор теряет TP, а
паросочетание находит.

Каждый вывод и каждая ошибка используются не более одного раза, поэтому копия
верного вывода автоматически становится FP — требование «Дубли не дают выгоды»
выполняется самой моделью сопоставления, без отдельной проверки на дубли.

## 7. Метрики

```
TP = размер максимального паросочетания
FP = len(findings) − TP
FN = len(truth.issues) − TP

P  = TP / (TP + FP)      при нулевом знаменателе P = 0
R  = TP / (TP + FN)      при нулевом знаменателе R = 0
F1 = 2*TP / (2*TP + FP + FN)
```

F1 считается **по формуле из задания напрямую**, а не как `2PR/(P+R)`: вторая
форма даёт 0/0 там, где задание требует конкретное значение.

Отдельные правила краёв (задание, раздел 05):

| Эталон | Выводы | F1 |
|---|---|---|
| пуст | пуст | **1** |
| пуст | непуст | **0** |
| непуст | пуст | 0 |

Единственный случай 0/0 в формуле `2TP/(2TP+FP+FN)` — это пусто/пусто, и он
равен 1. Остальные края формула закрывает сама.

## 8. Награда

```
return = clip(2*F1 − 1 − 0.002*inspection_steps, −1, 1)
```

Договорённости, которых нет в задании дословно и которые надо закрепить явно:

- `inspection_steps` — число **исследовательских** действий
  (`list_records`, `get_record`, `get_document`, `calculator`), включая
  ошибочные. Шаг самого `submit` в `inspection_steps` **не входит**.
- Счётчик авторитетно ведёт **среда** и передаёт оценщику. Оценщик его не
  пересчитывает по журналу.
- Округление только для отображения; балл считается до округления.
- Структурно неверный `submit` даёт `−1` без учёта шагов.
- Если 100-е действие исследовательское: `truncated=true`, оценивается **пустая**
  заявка. Этот итог надо отличать от невалидного `submit`.

### Контрольные значения (при 6 исследовательских шагах)

| Случай | TP/FP/FN | F1 | return |
|---|---|---|---|
| Полный верный ответ | 1/0/0 | 1 | 0.988 |
| Молчание при одной ошибке | 0/0/1 | 0 | −1 |
| Молчание на чистой книге | 0/0/0 | 1 | 0.988 |
| Ложное обвинение на чистой | 0/1/0 | 0 | −1 |
| Верный вывод и его копия | 1/1/0 | 2/3 | ≈ 0.3213 |
| Один верный среди 30 | 1/29/0 | 2/31 | ≈ −0.8830 |

Известный эффект, который надо описать честно в записке о дизайне: при усечении
на чистой книге пустая заявка даёт **положительный** возврат. Это следствие
общей формулы задания, а не наш баг. Частоту усечений показывать отдельной
метрикой.

## 9. Тесты как свойства порядка, а не только как значения

Задание (раздел 05) требует показать именно **неравенства**. Это отдельные
тесты, их нельзя заменить проверкой отдельных чисел:

```
R(полный верный ответ)  >  R(молчания)             на ошибочной книге
R(молчания)             >  R(ложного обвинения)    на чистой книге
R(верный ответ)         >  R(верный ответ + копия)
R(осмысленный ответ)    >  R(пометить всё)
R(ответ, s шагов) − R(тот же ответ, s+1 шаг) == 0.002   до границы clip
```

## 10. Что оценщик делать не имеет права

- Возвращать агенту числовую награду в закрытом режиме: всегда 0, в том числе на
  последнем шаге.
- Писать `truth`, `provenance`, `seed`, пути, stack trace, тайминги в
  наблюдения, тексты ошибок, `info` или `trajectories.jsonl`.
- Работать внутри процесса агента. Оценщик — отдельный доверенный процесс.
- Oracle собирает заявку **на стороне оценщика**, а не как политика, читающая
  `truth.json`. Oracle не является агентом и не живёт в `policies/`.

Утечка закрытых данных по заданию **блокирует оценивание целиком**, поэтому
раздел 10 важнее любой функциональности.
