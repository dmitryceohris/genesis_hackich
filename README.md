# RL-среда для дообучения моделей финансового аудита

**Команда:** Лесхан Уаис, Тухватуллина Дилайла, Оспан Салих

Genesis Hackathon, направление FinTech, онлайн-этап 19–22 ноября 2026 года.

Агент получает одну компанию и один отчётный период, запрашивает записи через
узкий набор инструментов и сдаёт выводы с доказательствами. Среда оценивает
результат и не обновляет веса модели.

Компании, люди, счета и суммы вымышлены. Это программная задача, не
аудиторское заключение.

## Состояние по зонам

| Зона | Каталоги | Состояние |
|---|---|---|
| Оценщик, политики, проверка эталона | `evaluator/`, `policies/`, `validator/`, `tests/`, `scripts/` | реализовано |
| Генератор данных | `generator/`, `integration/` | реализовано, четыре типа дефектов |
| Среда | `environment/` | реализовано |
| Изоляция агента контейнером | `Dockerfile.agent`, `runner/` | реализовано, сборка не проверена |

Эпизоды берутся из генератора (сиды 0..9) плюс четыре собранные руками
фикстуры для краёв формулы награды: чистая книга, усечение, взаимодействие.
Источник каждого эпизода помечен в артефактах полем `episode_source`, чтобы
прогон на сидах нельзя было принять за прогон на фикстурах и наоборот.

Что измерено на этом наборе (14 эпизодов, `artifacts/summary.json`):

| Политика | F1 | Возврат | Шагов | TP | FP | FN |
|---|---|---|---|---|---|---|
| oracle (сторона оценщика) | 1.000 | +1.000 | 0 | 44 | 0 | 0 |
| reconcile | 1.000 | +0.941 | 29.7 | 44 | 0 | 0 |
| random | 0.071 | −0.863 | 40.0 | 0 | 0 | 44 |
| flag_all | 0.000 | −1.000 | 8.0 | 0 | 336 | 44 |

`reconcile` даёт F1 = 1 на каждом эпизоде: решаемость и достижимость
доказательств не заявлены, а показаны. У `random` F1 не ноль только из-за
чистой книги, где молчание и есть верный ответ. `flag_all` обвиняет чистую
книгу и получает минимум.

## Требования

- Python 3.11 или новее.
- Зависимостей времени выполнения нет: только стандартная библиотека. Это
  проверяется шагом обязательного прогона, а не обещано на словах.
- Сеть не нужна. GPU не нужен.
- Целевые лимиты из задания: 2 ядра CPU, 4 ГБ RAM, 1 ГБ на решение,
  60 секунд на эпизод, 100 действий. Исходники занимают около 300 КБ.

## Наборы эпизодов

```
python scripts/build_episode_sets.py
```

Пишет `episodes/train/` и `episodes/dev/` — по 10 эпизодов каталогами из
восьми файлов, плюс `episodes/index.json` с сидами, настройками и вердиктом
независимой проверки по каждому. Каталог не версионируется: 20 эпизодов
восстанавливаются одной командой, а сиды и настройки записаны в индексе.

Наборы различаются не только сидами: в dev включены сценарии взаимодействия
дефектов. Правило отбора записано в индексе — берутся первые по порядку сиды,
которые строятся и проходят независимую проверку, а пропущенные перечислены в
`skipped` с причиной. Сейчас пропущен один: `seed=101`, где дубль счёта
попутно создаёт второе расхождение `period_cutoff`, которого нет в эталоне.
Перечислять пропуски обязательно, иначе отбор был бы незаметной подгонкой
набора под собственный валидатор.

## Единая команда проверки

```
make verify
```

Без `make` (например, на Windows) — то же самое напрямую:

```
python scripts/verify_all.py
```

Шесть шагов. Они не прерывают друг друга: при провале одного остальные всё
равно отчитываются, иначе одна опечатка скрывает состояние всей сдачи. Код
возврата ненулевой, если провалился хотя бы один шаг.

| Шаг | Что проверяет |
|---|---|
| версия Python | не ниже 3.11 |
| отсутствие сторонних зависимостей | импорты разобраны статически, `pytest` допускается только в `tests/` |
| тесты | контракт, награда, политики, парные проверки, утечки, внесение дефектов |
| независимая проверка данных и эталона | инварианты снимка, выводимость расхождений, достижимость доказательств |
| прогон базовых политик | метрики и запись траекторий |
| артефакты без закрытых данных | проверка записанного файла траекторий, а не объекта в памяти |

Отдельные цели: `make test`, `make reference`, `make baselines`, `make clean`.
На Windows: `make verify PYTHON=python`.

## Контейнеры

Их два, и назначение разное. `Dockerfile` прогоняет наши собственные тесты —
обязательную проверку. `Dockerfile.agent` запускает **чужой** код, политику
агента, и обязан не дать ему ни сети, ни записи, ни эталона.

### Изоляция агента

```
docker build -f Dockerfile.agent -t genesis-audit-agent .
```

```
docker run --rm --network none --read-only --cpus 2 --memory 4g --pids-limit 128 --cap-drop ALL --security-opt no-new-privileges -v "$PWD/episodes/train/EP-4E07408562BE:/episode:ro" -v "$PWD/artifacts/agent:/out" genesis-audit-agent --policy reconcile --episode-dir /episode --out /out/submission.json
```

Оба образа проверяются одной командой, которая сама скажет, что не сошлось:

```powershell
python scripts/check_images.py
```

Пять шагов: сборка образа проверки, обязательный прогон в нём с `--network
none`, сборка образа агента, прогон политики в изоляции и проверка, что в
образе агента физически нет ни `generator/`, ни `validator/`, ни
`evaluator/oracle.py`. Шаги не прерывают друг друга, код возврата ненулевой
при любом провале.

Что обеспечивает изоляцию, по пунктам:

| Чем | Что закрыто |
|---|---|
| в образ не скопированы `generator/`, `validator/`, `evaluator/oracle.py` | эталон недостижим физически, а не по договорённости |
| каталог эпизода смонтирован `:ro` | агент не может изменить данные под собой |
| `--network none` | сеть, и это же демонстрация офлайна |
| `--read-only` плюс `chmod -R a-w /app` | запись куда-либо, кроме смонтированного `/out` |
| `USER agent` (uid 10001, без оболочки и домашнего каталога) | работа от root |
| `--cap-drop ALL`, `--security-opt no-new-privileges` | повышение прав |
| `--cpus`, `--memory`, `--pids-limit` | исчерпание ресурсов хоста |
| точка входа `python -s -P` | подмена модуля стандартной библиотеки файлом рядом |

Награду контейнер не считает: оценщик внутрь не копируется, наружу выходит
только заявка и число исследовательских шагов. Оценку делает доверенная
сторона через `judge_adapter.score_episode`. Что агент не тянет путь к
эталону, проверяется тестом разбора импортов, а не обещанием
(`test_runner_never_imports_the_truth_side`).

### Обязательная проверка

#### Подготовка (нужна сеть, выполняется заранее)

```
docker build -t genesis-audit-verify .
docker save genesis-audit-verify -o genesis-audit-verify.tar
```

Перед сдачей базовый образ в `Dockerfile` закрепляется по digest, а не по тегу:
тег подвижен. Команда получения digest — в комментарии `Dockerfile`.

#### Автономный запуск (без сети)

```
docker load -i genesis-audit-verify.tar
docker run --rm --network none --cpus 2 --memory 4g genesis-audit-verify
```

`--network none` и есть демонстрация того, что проверка не обращается в сеть.
Образ не делает `pull` при запуске, потому что он уже загружен из архива.

```
                   provenance; точка входа generate_episode(seed, config, dir)
integration/       перевод схемы генератора в схему контракта оценщика
environment/       ядро среды (пять действий, 100 шагов, 60 секунд) и оболочка
                   протокола с режимами closed и train
evaluator/         валидация заявки, сопоставление, метрики, награда, oracle,
                   формат эпизода на диске
policies/          random, reconcile, flag_all — видят только наблюдения
validator/         независимая проверка публичного снимка и эталона

```

## Подключение жюри

```python
from judge_adapter import generate_episode, make_env, score_episode
```

`score_episode` возвращает ровно семь полей протокола: `tp`, `fp`, `fn`,
`precision`, `recall`, `f1`, `return`. На структурно неверной заявке
`return=-1`, остальные поля `null`.

Адаптер делегирует `generator.generate_episode` и `environment.make_env`. Оба
пакета есть, поэтому флаги `GENERATOR_IS_PLACEHOLDER` и
`ENVIRONMENT_IS_PLACEHOLDER` равны `False`; они оставлены, потому что это
проверяемый факт, а не фраза в документации, и тест на них есть.

`make_env(mode)` даёт два режима. В `closed` (по умолчанию) числовая награда
интерфейса всегда 0, включая последний шаг: итог забирает доверенная сторона
через `score_episode` или `env.report()`. В `train` на `submit` возвращается
терминальная награда официального оценщика. Награду считает только оценщик —
среда её не выдумывает и дважды по-разному оценить эпизод не может.

Канонические таблицы: `ledger`, `invoices`, `payments`, `fx`. Дополнительно
документирована таблица `policy`: каждое правило — отдельная запись, получаемая
через `get_record("policy", "<rule_id>")`. Это обязательно, потому что наборы
доказательств ссылаются на правила, а недостижимый `evidence_id` делает вывод
ложным.

Эпизод на диске (`evaluator/episode_io.py`): `manifest.json`, `ledger.csv`,
`invoices.jsonl`, `payments.jsonl`, `fx.csv`, `policy.json` и закрытые
`truth.json`, `provenance.json`. В CSV отсутствующая ссылка записана буквальным
маркером `null`; денежные поля читаются целыми, курс FX остаётся десятичной
строкой.

## Соответствие официальным определениям проверок

Определения проверок от 20 ноября 2026 года воспроизведены в
`tests/test_official_checks.py`: двадцать тестов блока 3 и открытые примеры
M01-M12, с их фикстурами и их числами. Все проходят.

Сверка нашла три расхождения, и все три исправлены: выдуманный `evidence_id`
больше не приносит TP (M04), код валюты в другом регистре даёт FP, а не −1
(M06), порядок тай-брейка приведён к `(issue_id, индекс вывода)`. Подробности в
`DESIGN.md`, разделы 9.6-9.8.

Два решения, которые видны по структуре и объяснены в `DESIGN.md`:

- **Oracle не политика.** Он живёт в `evaluator/oracle.py` и вызывается
  доверенным процессом вне контейнера агента. Политика, читающая `truth.json`,
  была бы каналом утечки эталона, а утечка блокирует оценивание целиком.
- **Валидатор не получает эталон.** `validator.reconstruct` принимает публичный
  снимок, и доступа к `truth` у него нет по сигнатуре, а не по договорённости.
  Сравнение делает отдельная доверенная обвязка.

Здесь же честная граница этой независимости, и она измерена, а не только
названа. `integration/episode_adapter.py` берёт сумму, валюту и наборы
доказательств каждой ошибки из той же `reconstruct`, а не из записи о
внесении, поэтому по этим полям валидатор проверяет собственный вывод.

Чтобы это не оставалось словами, адаптер сверяет два независимых вывода об
одной ошибке — что записал генератор при внесении и что восстановлено из
публичных записей — и пишет расхождения в
`provenance.derivation_disagreements` с обоими значениями.

**Расхождений о факте нет: 0 из 10 эпизодов по всем четырём типам** — тип,
сумма и валюта совпадают, наборы затронутых записей пересекаются. Эталон
берёт числа из реконструкции, но те же числа независимо записал генератор при
внесении, поэтому подтверждение больше не круговое. Тест
`test_no_type_disagrees_about_the_facts` падает и называет оба значения, если
одна из сторон разойдётся с другой.

Так было не сразу. Сверка нашла систематическое расхождение ровно на налог:
генератор считал весь продублированный или сдвинутый документ
(`total_minor`), реконструкция — только расходное плечо проводки. Прав был
генератор: книги искажены на всю сумму документа, налог включительно.
Исправлено в `validator/reconstruction.py` и `policies/reconciliation_agent.py`
одновременно, иначе политика сверки перестала бы попадать в эталон.

Осталась разница в именовании: генератор называет оба счёта, реконструкция —
счёт и строку журнала. Наборы пересекаются по счёту-дублю, то есть говорят об
одном событии разными словами. Это пишется отдельным полем
`provenance.affected_ids_naming` и расхождением о факте не считается —
смешивать одно с другим значило бы обесценить таблицу расхождений.

### Про `fx_conversion`

Этот тип держится на валютном плече платежа (`generator/settlement.py`). Часть
платежей уходит в банк в иностранной валюте: денежная строка журнала несёт две
суммы — списанную со счёта (`source_minor` в `source_currency`) и отражённую в
книге по курсу на дату платежа. Разницу округления забирает счёт курсовой
разницы, как и положено в учёте.

Ошибка вносится в проводку, а не в справочник курсов: пересчёт выполнен по
курсу другой даты. Тогда искажена именно отражённая сумма, разница вычисляется
из денежной строки и фиксинга, и её находят и oracle, и политика сверки.

Так было не сразу. До валютного плеча книга была одновалютной: таблица из 1460
фиксингов не использовалась ни одной проводкой, искажение курса не меняло ни
одной суммы, у ошибки стояло `claimed_amount_minor: null`, и независимая
реконструкция её не выводила ни на одном сиде. Такую ошибку в эталон вносить
нельзя — честный агент терял бы на ней recall без шансов, — поэтому тип был
выключен, а правило сохранилось в коде: ошибка, которую реконструкция не
выводит, уходит в `provenance.undeclarable` с причиной, а не в эталон. Тест на
это правило есть.

Измеренное ограничение: на сиде 14 дубль счёта выпадает за период и создаёт
второе настоящее расхождение `period_cutoff`, которого в эталоне нет. В набор
сдачи этот сид не входит, но дефект внесения существует, и валидатор его
находит (`undeclared_discrepancies`). Остальные 19 из 20 проверенных сидов
чистые.

Не проверено на машине разработки, и вот точная причина по каждому пункту.

Цель `make verify` — `make` на машине не установлен, запускался
`python scripts/verify_all.py` напрямую. Рецепты Makefile делегируют скриптам
и логики не содержат, но сам вызов через `make` не выполнялся.

Сборка образов — Docker Desktop 4.100 установлен, но движок не стартует:
Windows требует включить компонент `VirtualMachinePlatform`, а это полная
перезагрузка системы. Перед сдачей её решили не делать: образы и команды
запуска написаны и проверены на синтаксис, но `docker build` не выполнялся ни
для `Dockerfile`, ни для `Dockerfile.agent`. Одна команда для проверки обоих
образов — `python scripts/check_images.py`, она же пишет, что именно не
сошлось.

Digest базового образа — следствие предыдущего: получить его можно только
`docker pull`, поэтому в обоих Dockerfile остался тег `python:3.11-slim`, а
команда получения digest записана комментарием рядом с `FROM`.

Прогон под Python 3.11 — локально доступен только 3.14. Код написан под 3.11,
минимальная версия проверяется первым шагом обязательного прогона, но
фактического прогона на 3.11 не было.
