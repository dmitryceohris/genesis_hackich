# RL-среда для дообучения моделей финансового аудита

Агент получает одну компанию и один отчётный период, запрашивает записи через
узкий набор инструментов и сдаёт выводы с доказательствами. Среда оценивает
результат и не обновляет веса модели.

Компании, люди, счета и суммы вымышлены. Это программная задача, не
аудиторское заключение.

## Состояние по зонам

| Зона | Каталоги | Состояние |
|---|---|---|
| Оценщик, политики, проверка эталона | `evaluator/`, `policies/`, `validator/`, `tests/`, `scripts/` | реализовано |
| Генератор данных | `generator/`, `integration/` | реализовано, три типа дефектов из четырёх |
| Среда | `environment/` | реализовано |
| Изоляция агента контейнером | — | **не начато** |

Эпизоды берутся из генератора (сиды 0..9) плюс четыре собранные руками
фикстуры для краёв формулы награды: чистая книга, усечение, взаимодействие.
Источник каждого эпизода помечен в артефактах полем `episode_source`, чтобы
прогон на сидах нельзя было принять за прогон на фикстурах и наоборот.

Что измерено на этом наборе (14 эпизодов, `artifacts/summary.json`):

| Политика | F1 | Возврат | Шагов | TP | FP | FN |
|---|---|---|---|---|---|---|
| oracle (сторона оценщика) | 1.000 | +1.000 | 0 | 34 | 0 | 0 |
| reconcile | 1.000 | +0.941 | 29.6 | 34 | 0 | 0 |
| random | 0.071 | −0.863 | 40.0 | 0 | 0 | 34 |
| flag_all | 0.000 | −1.000 | 7.9 | 0 | 336 | 34 |

`reconcile` даёт F1 = 1 на каждом эпизоде: решаемость и достижимость
доказательств не заявлены, а показаны. У `random` F1 не ноль только из-за
чистой книги, где молчание и есть верный ответ. `flag_all` обвиняет чистую
книгу и получает минимум.

## Требования

- Python 3.11 или новее.
- Зависимостей времени выполнения нет: только стандартная библиотека. Это
  проверяется шагом обязательного прогона, а не обещано на словах.
- Сеть не нужна. GPU не нужен.
- Целевые лимиты из задания: 2 ядра CPU, 4 ГБ RAM, 1 ГБ на решение,
  60 секунд на эпизод, 100 действий. Исходники занимают около 300 КБ.

## Единая команда проверки

```
make verify
```

Без `make` (например, на Windows) — то же самое напрямую:

```
python scripts/verify_all.py
```

Шесть шагов. Они не прерывают друг друга: при провале одного остальные всё
равно отчитываются, иначе одна опечатка скрывает состояние всей сдачи. Код
возврата ненулевой, если провалился хотя бы один шаг.

| Шаг | Что проверяет |
|---|---|
| версия Python | не ниже 3.11 |
| отсутствие сторонних зависимостей | импорты разобраны статически, `pytest` допускается только в `tests/` |
| тесты | контракт, награда, политики, парные проверки, утечки, внесение дефектов |
| независимая проверка данных и эталона | инварианты снимка, выводимость расхождений, достижимость доказательств |
| прогон базовых политик | метрики и запись траекторий |
| артефакты без закрытых данных | проверка записанного файла траекторий, а не объекта в памяти |

Отдельные цели: `make test`, `make reference`, `make baselines`, `make clean`.
На Windows: `make verify PYTHON=python`.

## Контейнер

Образ предназначен для **обязательной проверки**. Контейнер изоляции агента —
отключённая сеть, read-only root, отдельный непривилегированный процесс без
секретов, лимиты на память, CPU и объём вывода — относится к зоне среды и ещё
не реализован.

### Подготовка (нужна сеть, выполняется заранее)

```
docker build -t genesis-audit-verify .
docker save genesis-audit-verify -o genesis-audit-verify.tar
```

Перед сдачей базовый образ в `Dockerfile` закрепляется по digest, а не по тегу:
тег подвижен. Команда получения digest — в комментарии `Dockerfile`.

### Автономный запуск (без сети)

```
docker load -i genesis-audit-verify.tar
docker run --rm --network none --cpus 2 --memory 4g genesis-audit-verify
```

`--network none` и есть демонстрация того, что проверка не обращается в сеть.
Образ не делает `pull` при запуске, потому что он уже загружен из архива.

```
                   provenance; точка входа generate_episode(seed, config, dir)
integration/       перевод схемы генератора в схему контракта оценщика
environment/       ядро среды (пять действий, 100 шагов, 60 секунд) и оболочка
                   протокола с режимами closed и train
evaluator/         валидация заявки, сопоставление, метрики, награда, oracle,
                   формат эпизода на диске
policies/          random, reconcile, flag_all — видят только наблюдения
validator/         независимая проверка публичного снимка и эталона

```

## Подключение жюри

```python
from judge_adapter import generate_episode, make_env, score_episode
```

`score_episode` возвращает ровно семь полей протокола: `tp`, `fp`, `fn`,
`precision`, `recall`, `f1`, `return`. На структурно неверной заявке
`return=-1`, остальные поля `null`.

Адаптер делегирует `generator.generate_episode` и `environment.make_env`. Оба
пакета есть, поэтому флаги `GENERATOR_IS_PLACEHOLDER` и
`ENVIRONMENT_IS_PLACEHOLDER` равны `False`; они оставлены, потому что это
проверяемый факт, а не фраза в документации, и тест на них есть.

`make_env(mode)` даёт два режима. В `closed` (по умолчанию) числовая награда
интерфейса всегда 0, включая последний шаг: итог забирает доверенная сторона
через `score_episode` или `env.report()`. В `train` на `submit` возвращается
терминальная награда официального оценщика. Награду считает только оценщик —
среда её не выдумывает и дважды по-разному оценить эпизод не может.

Канонические таблицы: `ledger`, `invoices`, `payments`, `fx`. Дополнительно
документирована таблица `policy`: каждое правило — отдельная запись, получаемая
через `get_record("policy", "<rule_id>")`. Это обязательно, потому что наборы
доказательств ссылаются на правила, а недостижимый `evidence_id` делает вывод
ложным.

Эпизод на диске (`evaluator/episode_io.py`): `manifest.json`, `ledger.csv`,
`invoices.jsonl`, `payments.jsonl`, `fx.csv`, `policy.json` и закрытые
`truth.json`, `provenance.json`. В CSV отсутствующая ссылка записана буквальным
маркером `null`; денежные поля читаются целыми, курс FX остаётся десятичной
строкой.

## Соответствие официальным определениям проверок

Определения проверок от 20 ноября 2026 года воспроизведены в
`tests/test_official_checks.py`: двадцать тестов блока 3 и открытые примеры
M01-M12, с их фикстурами и их числами. Все проходят.

Сверка нашла три расхождения, и все три исправлены: выдуманный `evidence_id`
больше не приносит TP (M04), код валюты в другом регистре даёт FP, а не −1
(M06), порядок тай-брейка приведён к `(issue_id, индекс вывода)`. Подробности в
`DESIGN.md`, разделы 9.6-9.8.

Два решения, которые видны по структуре и объяснены в `DESIGN.md`:

- **Oracle не политика.** Он живёт в `evaluator/oracle.py` и вызывается
  доверенным процессом вне контейнера агента. Политика, читающая `truth.json`,
  была бы каналом утечки эталона, а утечка блокирует оценивание целиком.
- **Валидатор не получает эталон.** `validator.reconstruct` принимает публичный
  снимок, и доступа к `truth` у него нет по сигнатуре, а не по договорённости.
  Сравнение делает отдельная доверенная обвязка.

Здесь же честная граница этой независимости, и её стоит знать заранее.
`integration/episode_adapter.py` берёт сумму, валюту и наборы доказательств
каждой ошибки из той же `reconstruct`, а не из записи о внесении. То есть по
этим полям валидатор проверяет собственный вывод, и проверка проходит
тривиально. Независимыми остаются: сам факт внесения (он из `provenance`
генератора), инварианты снимка, достижимость каждого ID через инструменты и
поиск расхождений, о которых эталон молчит — последнее на сиде 14 как раз
сработало. Правильный порядок — строить сумму и доказательства из записи о
внесении, а реконструкцию оставить проверкой; это не успело войти в сдачу и
описано в `DESIGN.md`, раздел 10.

### Про `fx_conversion`

Тип реализован в генераторе, но **выключен в настройке по умолчанию**, и это
осознанный выбор, а не недосмотр. Генератор строит одновалютную книгу: счёта,
платежи и проводки все в базовой валюте, а таблица фиксингов ни одной
проводкой не используется. Поэтому искажение курса не даёт искажённой суммы:
независимая реконструкция такого расхождения не выводит ни на одном из 20
проверенных сидов, а по контракту объявлять в эталоне ошибку, которую нельзя
доказать публичными записями, нельзя — честный агент терял бы на ней recall
без шансов.

Включить обратно: `config["error_types"]` плюс `"fx_rate"`. Тогда ошибка
попадает не в эталон, а в `provenance.undeclarable` с причиной —
диагностируемо, а не молча. Правильное исправление — валютное плечо платежа:
платёж в иностранной валюте, денежная строка с `source_minor` и
`source_currency`, разница на счёте курсовых разниц. Оценщик, политика сверки и
валидатор это уже умеют и ждут только данных.

Ещё одно измеренное: на сиде 14 дубль счёта выпадает за период и создаёт второе
настоящее расхождение `period_cutoff`, которого в эталоне нет. В набор сдачи
этот сид не входит, но дефект внесения существует, и валидатор его находит
(`undeclared_discrepancies`).

Не проверено на машине разработки: цель `make verify` (`make` не установлен,
запускался `scripts/verify_all.py` напрямую), сборка образа (`docker` не
установлен) и прогон под Python 3.11 — локально доступен только 3.14. Код
написан под 3.11, минимальная версия проверяется первым шагом обязательного
прогона.
